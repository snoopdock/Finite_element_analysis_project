# G3.4.17 — Evidence-gated SAT learning rule candidates

## Intended use

This stage introduces **candidate rules**, not approved, learned, or automatically enforced SAT policies. Each candidate records a statement, applicability, its concrete decision/action/outcome provenance, limitations, and an explicit manual-review gate. An audit consumer can trace from the candidate to branch-tracked records and a validation report digest; **a digest alone cannot retrieve an expired GitHub artifact or prove the truth of a lesson**.

## Critical observation in the G3.4.16 records

- G3.4.15's sample action has `outcome.status: pending`.
- G3.4.16's example feedback has `result.status: successful`.
- The G3.4.16 targeted CI run passed a single test verifying that two dictionary keys exist.

These facts do not establish that the underlying engineering action was successful. Rule candidates carrying this relationship must disclose `pending_action_with_successful_feedback`. Promotion is not supported by this milestone; a reviewer must independently determine what happened before relying on such a rule.

## Files

- `decision_memory/learning_rules.py`: read-only validator and graph projection tool.
- `decision_memory/learning_rule_schema.json`: versioned candidate-policy schema.
- `decision_memory/rules/RULE-G3.4.17-001.yaml`: unapproved example using actual earlier decision/action/outcome references and the G3.4.16 evidence report digest.
- `tests/semantic_high_assurance/test_learning_rule_candidates.py`: positive/negative tests for cross-links, confidence boundaries, YAML safety, and promotion restrictions.
- `validation/profiles/G3.4.17.yaml`: standard manual validation profile; existing dispatcher works unchanged.

## Usage through GitHub Actions

Use the **existing** `Manual Validation Dispatcher` in `main` (`workflow_dispatch`). Specify `stage1/section-uuids` as branch and `G3.4.17` as profile. The profile requests targeted tests and full regression. No `push` trigger is added and no local execution is required.

Optional direct audit command (for maintainers using a Python environment):

```sh
python decision_memory/learning_rules.py --repository . --output rule-audit.json
```

The audit projection includes rule IDs, source record IDs, declared validation profiles, observed discrepancies, and a hardcoded false flag for automatic SAT execution. It does **not** interpret natural-language claims, retrieve evidence artifacts, connect to a SAT solver, infer causal impact, or implement rule promotion. Those are future reviewed integrations.

## Design constraints for future work

1. Never equate a schema contract test with engineering impact.
2. Preserve uncertainty and disagreements rather than silently selecting a successful status.
3. Require evidence references to be resolvable; external report digests are *identifiers*, not live proof.
4. Require a separate human-approved policy for promotion; no candidate may become executable merely because validation succeeds.
5. Keep learning-rule memory in git-tracked text; avoid permanent retention of large raw CI logs unless independently justified.
