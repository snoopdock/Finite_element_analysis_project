# G3.4.10 — Content-Addressed Validation Evidence Publication

## Purpose and trust boundary

G3.4.9 establishes semantic consistency for evidence generated by the manual GitHub dispatcher. G3.4.10 adds a deterministic, content-addressed **packaging and publication** boundary to preserve the exact bytes accepted by that verification step.

The new `EvidenceBundleStore` publishes `SHA256(bundle-bytes).validation.zip` under a caller-selected directory and returns a receipt with the bundle hash, report hash, size, and whether this operation performed the first commit.

The canonical bundle includes the original report, detached report hash, engine test log, declared targeted/regression JUnit and logs, and `bundle_manifest.json`, which individually binds all members by SHA-256 and byte size. It does not insert a publication timestamp or other non-deterministic data into the bundle.

## Publication algorithm

1. Reject unsafe source files and names; read exact bytes through non-following file descriptors; enforce file count and byte limits.
2. Validate report JSON version, detached digest, file records, JUnit count consistency and basic outcome invariants.
3. Produce an uncompressed ZIP with stable ordering, metadata and canonical manifest.
4. Verify the completed bundle in memory.
5. Write it to an exclusive temporary file, `fsync` the content and atomically hard-link into the CAS root; **never overwrite** an existing CAS key.
6. If a concurrent publication already committed the key, reopen and verify that exact object, returning `committed=false`.
7. `fsync` the store directory on POSIX, remove the staging file, and return the receipt.

**Scope:** Requires a local filesystem supporting atomic same-filesystem hard links and directory fsync; the standard GitHub Ubuntu runner satisfies this. A hard-link commit avoids `os.replace` overwriting existing objects. This is an append-only *API* contract, not tamper-proof storage against a filesystem owner or administrator.

## GitHub workflow integration

The `main` dispatcher has one extra step, **Publish verified evidence into immutable bundle**, between evidence verification and artifact upload. It runs only when the trusted `verify_validation_evidence.py` step succeeds. The runner is still triggered only by `workflow_dispatch`, and no branch-specific workflow or engine copy is required.

The new command on `stage1/section-uuids`, `tools/publish_validation_evidence_bundle.py`, publishes a content-addressed ZIP in a temporary job-local CAS, verifies it, copies it into `validation-artifacts/bundles/`, and adds `bundle_receipt.json` and `bundle_receipt.sha256` to the existing downloadable GitHub artifact. Because the existing artifact upload uses `if: always()`, failure diagnostics remain available even if this publication step fails.

The receipt binds the same `profile_id`, development Git SHA, engine SHA, and GitHub run identifiers as the input report. It is a digest-bound receipt, **not a digital signature**. GitHub Actions artifact retention remains 30 days unless changed by repository maintainers; temporary runner storage is not a persistent CAS.

## Verification boundaries

This code validates deterministic byte identity, report links, basic JUnit counts, path safety, and safe publication. It does **not** substitute for the independent main-branch verifier, authenticate a GitHub identity, prove scientific validity of results, or check UNSAT logical correctness.

## Validation

The branch profile `G3.4.10.yaml` selects the focused `test_validation_evidence_store.py` tests and full repository regression. No extra workflow needs to be copied to the development branch.

The manual run configuration remains:

- Workflow from: `main`
- Branch: `stage1/section-uuids`
- Profile: `latest` (selects G3.4.10)
- Regression mode: `profile`

The output `manual-validation-evidence-<run>-<attempt>` should contain the existing report/JUnit/log files **plus** `bundles/<sha>.validation.zip`, `bundle_receipt.json`, and `bundle_receipt.sha256`.
