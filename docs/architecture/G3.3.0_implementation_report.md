# G3.3.0 Implementation Report — Audit Orchestration and Cost-Aware Verification Foundation

## Purpose

G3.3.0 adds a deterministic control plane for choosing and executing verification work under explicit resource constraints. It builds above G3.1 verification semantics and G3.2 change/replay infrastructure; it does not replace either.

## Runtime architecture

```text
VerificationObligations
        +
VerificationObjectives
        +
VerifierRegistry
        +
VerifierResourceProfiles
        +
AuditBudget / OrchestrationPolicy
        |
        v
Cost-Aware Planner
        |
        v
OrchestrationPlan
        |
        v
Bounded Orchestration Executor
        |
        v
VerificationReceipts + Execution Trace
```

The executor does not create findings, mutate graph state, or write long-term memory.

## Main implementation

The package `audit_engine.semantic_audit.orchestration` introduces:

- `VerifierOrchestrationProfile` and `VerifierProfileCatalog`;
- `AuditBudget`;
- `VerificationObjective`;
- `OrchestrationPolicy`;
- deterministic two-pass budget reservation;
- `VerificationRoute` and `OrchestrationPlan`;
- bounded fallback execution;
- execution/result artifacts;
- JSON serialization helpers;
- an orchestration service facade.

The verifier registry receives one non-breaking extension: `compatible(obligation)` enumerates semantically compatible verifiers while leaving all cost decisions outside the verification package.

## Planning semantics

The initial strategy is `minimum_cost_sufficient`.

A candidate verifier is eligible only when:

1. the registry says it supports the obligation;
2. the obligation's requested-verifier restrictions permit it;
3. a version-matching orchestration profile exists;
4. the profile's maximum evidence state can satisfy the objective;
5. the method is permitted by policy;
6. the execution mode is permitted by the budget;
7. side-effect requirements are satisfied.

The planner first reserves one primary verifier per objective in operational-priority order. Remaining budget may then reserve fallbacks. This prevents an early objective from consuming all budget on optional fallback work before other objectives receive primary coverage.

Unscheduled work is retained explicitly as `unscheduled_no_capability`, `unscheduled_policy`, or `unscheduled_budget`.

## Execution semantics

Only planned verifier IDs may execute. Every execution consumes the cost declared in the sealed plan. Both cost and verifier-run limits are rechecked during execution independently of planner correctness.

A route stops when a receipt:

- has a terminal `CONFIRMED` or `REFUTED` decision; and
- satisfies the objective's minimum evidence state.

An inconclusive result may advance to a planned fallback. Errors do not fall back unless policy explicitly permits it.

## Security boundary

Evidence and verifier output are data, not orchestration instructions. The current executor cannot dynamically expand its plan from source text, graph metadata, receipt details, or LLM output. Sandboxed/external execution must be explicitly enabled in the budget.

## Validation

G3.3.0 adds a dedicated test suite and deterministic acceptance artifact. The validator checks budget enforcement, fallback behavior, no implicit verifier cost, explicit execution-mode permission, lack of finding/memory side effects, and deterministic plan/execution identities.

## Deferred work

G3.3.0 intentionally defers:

- measured runtime calibration;
- expected-information-gain learning;
- solver/executable verifier implementations;
- adaptive replanning;
- asynchronous/background execution;
- finding creation from orchestration;
- long-term orchestration memory;
- neural/GNN prioritization.

Those features require separate contracts so operational heuristics cannot silently acquire semantic authority.
