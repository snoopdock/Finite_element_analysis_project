# G3.4.12 — Evidence Catalog Integrity and Manual Historical Retrieval

## Background and repair to G3.4.11

The G3.4.11 catalog-only workflow correctly selected `G3.4.11` in the October 10 GitHub log, but did **not** execute the original pytest/evidence chain. The change in this patch restores the last known working G3.4.10 manual validation dispatcher and adds catalog publication only *after* independent verification and CAS bundle publication.

The `latest` selector is resolved by `tools/validation_registry_runner.py` (already on main), which uses numeric version ordering instead of lexical ordering. The G3.4.11 `tools/validation_catalog.py` implementation is replaced with a strict verifier and index builder.

## Trust and threat model

A successful catalog step requires all of:

1. Main's validation engine has executed its unit tests, the requested profile's targeted pytest tests, and any required regression suite.
2. Main's independent evidence verifier has accepted the report, JUnit records, and checked-out Git provenance.
3. The development branch's G3.4.10 publisher has created an immutable CAS bundle and a detached receipt.
4. Main's catalog engine checks exact report and receipt SHA-256 bindings, the physical bundle SHA-256 and length, the canonical bundle manifest, member hashes, and report bytes inside the bundle.
5. The catalog engine writes `catalog/catalog_entry.json`, `catalog/catalog_entry.sha256`, `catalog/index.json`, and `catalog/index.sha256` and independently re-verifies them.
6. GitHub Actions uploads all files under `validation-artifacts` even if an earlier validation step fails. Catalog creation is skipped if verified CAS publication did not succeed.

Hash integrity is **not** signing, third-party attestation, or proof that GitHub itself is trustworthy. A user with the ability to modify all evidence bytes could recompute checksums; prior trusted CI checks and repository provenance are separate trust assumptions.

## Catalog record

Each catalog entry records a content-addressed bundle ID, exact byte size, SHA-256 of report and receipt, versioned profile, target branch, source and engine commit SHAs, GitHub run ID and attempt, actual passed targeted-test count, and regression status. The branch-side `validation/catalog/schema.json` describes the record. The trusted main script enforces the actual data contract independently of branch-supplied schemas.

A catalog index in a given downloaded artifact describes **that run only**. It is not an automatically persisted GitHub-wide database. Retrieval of previously uploaded artifacts is provided as a separate manual GitHub workflow using `actions/download-artifact`. Catalogs are independently verified at query time.

## Running from GitHub only

### New validation

1. Put the `MAIN_BRANCH` files from the ZIP in `main` (replace the existing central dispatcher and catalog tool; add the new retrieval workflow and main engine test file).
2. Put the `STAGE1_SECTION_UUIDS` files in `stage1/section-uuids`.
3. From GitHub → Actions → **Manual Validation Dispatcher** → Run workflow, select `main` as the workflow source and set branch `stage1/section-uuids`, profile `G3.4.12` (or `latest`), regression mode `profile`.
4. Wait for targeted/regression tests and independent verification, then download `manual-validation-evidence-<run_id>-<attempt>`; it should contain `catalog/` and `bundles/`.

### Historical retrieval (also manual)

1. Open Actions → **Manual Validation Evidence Retrieval** → Run workflow from `main`.
2. Provide `source_run_id` (from the original successful validation run URL) and `source_attempt` (usually `1`). Optionally provide expected profile and source commit SHA.
3. The workflow downloads the original artifact with GitHub's read-only token, independently validates the bundle and catalog, and outputs matching records. If the historical artifact predates G3.4.12 and has no catalog, it reconstructs a per-run catalog after verifying the original bundle and receipt.
4. Read the workflow log or download `historical-validation-verification-<run_id>`.

Both workflows use **only** `workflow_dispatch`. There is no push or pull-request trigger.

## Scope limitations

* Artifact retrieval is limited to GitHub's artifact retention window and the Actions token's read permissions.
* The retrieval workflow accepts a known run ID; it does not enumerate every run in the repository or maintain a persistent central index.
* Source branch tests and the main engine are separated by two checkouts. Do not copy the engine script to the development branch.
* GitHub must validate G3.4.12 in its own environment; local focused tests cannot replace the manual full workflow.
