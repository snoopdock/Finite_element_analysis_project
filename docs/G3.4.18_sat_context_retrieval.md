# G3.4.18 — Decision Memory Retrieval and SAT Context Preparation

## Goal

Offer **read-only, auditable context** from the existing decision-memory graph to people and future SAT research components. Retrieval does not approve rules, infer real engineering success, select actions or write back to memory. It does not give stored text instruction authority.

## Inputs and outputs

The target branch provides `decision_memory/decisions/`, `actions/`, `outcomes/`, `rules/`, and `validation/profiles/`. All record contents are treated as **untrusted historical assertions**. Before retrieving any hits the engine performs G3.4.17 candidate-rule graph validation (`learning_rules.inspect_repository`). It rejects unsupported schemas, dangerous YAML, invalid or dangling rule links, symlinked source files, oversized records and unapproved rule promotions.

For each matching item, context includes:

- record type and ID;
- relative repository source path and the **SHA-256 of that source file**;
- deterministic lexical match score and matched query terms;
- a short, explicitly **untrusted** excerpt;
- grounded links to related records with individual source hashes;
- flags for pending actions, unresolved references, human review, historical contradictions and unverified engineering impact.

At the envelope level it reports `source_commit_sha` only when the source is an actual Git checkout; otherwise `null`. `context_sha256` hashes canonical output **before adding the digest field**, to detect accidental alteration. These digests do not authenticate the repository author and are not signatures.

The output is deliberately deterministic for the same query and source data, except that Git identity can be absent in non-Git snapshots. Matches are ranked as token intersections (ID match 5, excerpt match 3, other data match 1). **Scores are not probabilities or confidence metrics**, and zero matches produce an empty list rather than a fabricated recommendation. No embeddings, language-model inference, outbound network, or executable SAT rule engine are included.

## Manual GitHub operation (no local runtime)

1. Copy `MAIN_BRANCH/.github/workflows/06_manual_sat_memory_context.yml` into the `.github/workflows/` folder of **main** once. This is a separate manual query workflow and does not replace the existing validation dispatcher.
2. Copy all `STAGE1_SECTION_UUIDS/` contents to their same relative paths on `stage1/section-uuids`.
3. Validate through **Actions → Manual Validation Dispatcher**, with branch `stage1/section-uuids`, profile `G3.4.18`, regression mode `profile`.
4. To query records, open **Actions → Manual SAT Decision Memory Context Retrieval → Run workflow** (workflow from `main`), supply the target branch, a query such as `schema validation engineering impact`, and a result limit. The result is printed in the job log and uploaded as `sat-context.json`.

The GitHub context JSON artifact has short retention and is **transport only**. The durable memory is the source-controlled `decision_memory/` records; there is no requirement to permanently store every query output.

## Safety and evidence semantics

- `automated_sat_action_allowed: false`, `human_review_required: true` and `eligible_for_automatic_sat_execution: false` are invariant.
- Candidate learning rules are marked as **not approved**, even when their contracts passed tests.
- A successful outcome record alongside an action marked `pending` is explicitly flagged as a **discrepancy**.
- Referenced external validation report hashes are identifiers; **their external bytes are not reverified** during search.
- Historical record prose is data and cannot modify engine policy or tell SAT what to execute.
- The retrieval engine never modifies the decision records. It writes JSON only when explicitly given `--output` outside the source checkout.
- `source_commit_sha` and file hashes give traceability to a particular retrieved state. Trusting an artifact's author or the quality of an engineering conclusion requires separate review and provenance validation.

## Future integration

When SAT actions are developed, expose this JSON only as a **retrieval context input** with citations and warning flags. Separate stages should verify relevant evidence bytes and evaluate decisions under current engineering constraints. Do not automatically translate candidate rules or retrieved prose into SAT clauses, code changes, or execution authorization.
