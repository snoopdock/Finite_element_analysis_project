# G9.39 — LLM Runtime Observability and Provider Contract Repair

## Objective

Improve the repository's ability to explain failures while an LLM provider is active. This patch is operational only: it does not change scientific-writing prompts, scientific-content requirements, section topics, convergence criteria, or authoring policies.

## Findings addressed

1. `core.pipeline.phase_extract` directly read `provider.total_calls`. `OpenAICompatibleProvider` exposed `logical_calls` and returned `total_calls` only inside `get_stats()`, so NaraRouter and OpenRouter crashed with `AttributeError` despite earlier successful calls.
2. A top-level pipeline exception exited before normal `model_usage` persistence, causing the benchmark summary to lose provider counters.
3. The benchmark used `GITHUB_SHA` as its commit identifier even though the pipeline checkout was the selected target branch. That confused the source revision with the workflow revision.
4. `errors_recorded` became null when state had no `errors` list, despite bullet errors being present in `output/validation_report.md`.
5. The benchmark did not include a phase-level provider telemetry artifact.

## Corrections

- Add an explicit provider-call counter compatibility contract (`logical_calls` preferred; `total_calls` supported; missing counters fail clearly).
- Expose `OpenAICompatibleProvider.total_calls` as a read-only alias to `logical_calls`.
- Record provider snapshots and usage deltas at research, extract, write, adjustment and assembly boundaries.
- Persist a credential-redacted `output/provider_runtime_diagnostics.json` on normal completion and uncaught failure.
- Preserve `model_usage`, run status and a structured failure phase when the pipeline crashes after provider initialization.
- Distinguish `source_commit` (actual checked-out FEA code) from `workflow_commit` (GitHub Actions definition commit).
- Count errors from state and the report without double-counting; include the runtime diagnostic artifact in the benchmark manifest.
- Add focused tests for provider counters, phase deltas, secret redaction, source/workflow commit provenance and report error counting.

## Audit-engine interpretation

The new artifact is operational evidence. It can establish which phase was active, whether provider calls increased during that phase, how many attempts succeeded or failed, what token usage the provider reported, and which exception stopped execution. It does not determine whether generated scientific content is correct.

## Safety and scope

- No prompts or scientific writing rules are changed.
- No automatic repair, repository mutation, commit, push or self-correction is enabled.
- Provider secrets are redacted from the runtime diagnostics.
- Existing high-budget authorization and final pipeline/publication gates remain in force.
- The benchmark remains manually triggered and read-only.
