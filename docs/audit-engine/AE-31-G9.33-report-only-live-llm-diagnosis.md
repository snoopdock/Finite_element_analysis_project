# AE-31 / G9.33 — Report-only live LLM diagnosis

## Purpose

AE-31 is the first controlled experiment that invokes the user's two configured
LLM gateways against a real repository-maintenance issue. It investigates the
recurring Semantic Scholar retrieval failures already recorded in
`state/current_state.json` and the implementation under `research/`.

The output is a plain-text report. It includes a proposed correction/diff when
models provide one, but **does not apply or execute any model-generated change**.
Automatic self-correction is explicitly out of scope until a later, separately
approved milestone adds trusted verification (including the planned Lean work).

## Why this is not forced through AE-28's existing response schema

AE-28 v1 is specifically designed to normalize semantic relationship
assertions into AE-27's candidate-only semantic proposal protocol. A diagnosis
of Python source, HTTP failure modes, and a proposed code diff is a different
response type. AE-31 therefore uses a separate strict diagnostic response
schema while reusing the same architectural principles: exact input digests,
source-bound evidence, model/request provenance, bounded input, and no model
authority. It binds a scoped repository snapshot and finding using the AE-29
`RepositorySnapshot` digest and finding/audit-report digest algorithms.

## Evidence supplied to the models

The runner reads a fixed allowlist of repository files as data only:

- `research/semantic_scholar.py`
- `research/evidence.py`
- `providers/cloudflare.py`
- `config.yaml`
- `state/current_state.json` (only a sanitized retrieval-status summary is sent;
  the full state bytes are hashed into the snapshot manifest)
- retrieval/acquisition tests
- AE-28/AE-29/AE-30 protocol documentation and evaluator source digests/content

The runner rejects symlinked input paths, checks path containment, enforces the
AE-29 file/byte budgets, and does not import or execute target-repository code.
It also performs exactly one low-volume, unauthenticated Semantic Scholar API
probe without retries. It records the HTTP status and selected rate-limit
headers when provided.

## Providers

- Cloudflare Workers AI: `CLOUDFLARE_ACCOUNT_ID` + `CLOUDFLARE_API_TOKEN`.
- NaraRouter: `NARAROUTER_API_KEY`; the authenticated `/v1/models` endpoint is
  queried when model input is `auto`. The documented `deepseek-3.2` alias is
  preferred when available; otherwise the first sorted account-visible model
  ID is recorded and used.

The same task/context is sent independently to each provider. Neither model
receives the other model's response. One generation call is made per provider;
no automatic retries are used for model calls. Secrets are never included in
prompts or report metadata and are redacted from captured text.

## Report contents

`AE31_Semantic_Scholar_Diagnosis.txt` includes:

- target branch and commit;
- AE-29-compatible scoped snapshot, finding, and audit digests;
- per-file SHA-256 manifest;
- historical retrieval-status summary;
- one live API probe result;
- deterministic source observations;
- each provider's status, model, raw output digest, structured diagnosis (if
  valid), evidence-reference checks, and proposed diff path-scope checks;
- cross-provider agreement/disagreement summary;
- the exact prompt and context sent to both models;
- explicit limitations and the human review question.

The report is created outside the target checkout and uploaded as an artifact.
The workflow has `contents: read` permissions only and has no schedule, push,
commit, merge, patch-apply, or repository-write step.

## Interpretation rules

- HTTP 429 is evidence of HTTP-level throttling for that request; it is not by
  itself proof of the upstream service's internal reason for throttling.
- Historical 429 records and the live probe are separate observations.
- API-search failures are distinct from later open-access PDF download/OCR
  failures.
- Model confidence or agreement is not verification.
- A proposed diff is a draft only. The path check is not proof that the diff is
  correct or applicable.
- No Semantic Scholar API key is assumed to exist. Code can improve rate-limit
  handling without one, but reliable access cannot be guaranteed solely by
  changing local code if upstream unauthenticated throttling continues.

## Validation

The G9.33 profile is deterministic and does not call live providers. It mocks
all network interactions and checks snapshot compatibility, response schema,
provider error handling, secret redaction, evidence references, path-scope
review, report-only behavior, and output path safety.

The separate manual workflow performs the live two-provider experiment. It is
not part of the G9.33 validation profile and does not mutate the repository.
