# AE-45.1 — Deterministic A/B rule catalog

**Status:** specifications registered; rules are not executable yet  
**Branch:** `stage1/section-uuids`  
**Depends on:** AE-45 A0 validated input/report contracts  
**Source basis:** pinned case task statements, declared scopes, fixture source and task-visible fixture contracts only

## 1. Boundary

The rule catalog is a specification registry, not an outcome table. It contains no case diagnosis, expected finding, provisional reference label, or benchmark score. It explicitly declares that rules may not read case `ground_truth` and may not promote primary benchmark eligibility.

The five registered rule families describe when deterministic evidence may support a scoped conclusion and when the engine must abstain:

1. Python control-flow unbound local at a return sink.
2. Exception-handler suppression against an explicit propagation contract.
3. Stale intermediate value bypassed at an output sink.
4. Complete initialization and contract satisfaction for a narrowly scoped property.
5. Unresolved dynamic attribute/provider contract, preserving observation while withholding a defect conclusion.

## 2. Evidence and rule authority

Each rule declares preconditions, sufficient evidence, counterevidence and abstention conditions. A rule cannot issue a diagnosis from a lexical witness alone. The decision authority is constrained:

- Defect authority requires every sufficient-evidence condition to hold and counterevidence checks to pass.
- No-defect authority is scoped to the named property and enumerated task-visible contract cases; it is not a claim that the whole repository is defect-free.
- Dynamic or incomplete provider evidence may support an observation but not a defect conclusion.
- Unsupported semantics, unresolved dependencies, incomplete scope or insufficient contract evidence require abstention.

The rule catalogue's fixture references use exact source commit SHAs. They identify rule exercises, counterexamples and insufficient-context exercises; they do not encode expected diagnostic labels.

## 3. Case evidence used to formulate the specifications

- The branch-control fixture shows a function-local assigned only under a condition and returned afterward; its task-visible expected-behavior file enumerates both true and false inputs. The complete-initialization control supplies a counterexample where a default assignment precedes the conditional.
- The exception fixture declares an `OSError` propagation contract; its function catches `OSError` and returns a fallback mapping.
- The data-flow fixture declares an invoice formula and expected output; the function assigns a discounted intermediate but its return expression uses the original subtotal.
- The provider-interface fixture shows a consumer read of `total_calls` and a visible adapter with a `calls` field, but no complete runtime contract is established in the supplied source.
- The ambiguous provider fixture explicitly describes an unresolved dynamic factory/import boundary and says the missing implementation prevents ruling out wrappers, inheritance or generated attributes.

These observations support rule design only. They do not establish independent gold labels, and the catalog was not populated from the hidden expected findings in case records.

## 4. Implementation status

Files:

The validator checks the strict schema, unique rule IDs, exact source-SHA format, safe fixture paths, duplicate fixture references and the non-promotion boundary. It does not execute a rule or calculate a case outcome.

## 5. Acceptance boundary and next step

A1 is complete only when the catalog validator and tests pass in the full AE-32D workflow. This establishes specification integrity, not diagnostic correctness.

Next, A2 should implement a small, explicitly supported Python AST/CFG subset and safe expression interpreter. Each executable rule needs unit fixtures for its sufficient-evidence, counterevidence and abstention branches. The engine must reject unsupported syntax rather than guess. No condition runner should emit a completed diagnostic decision until those rule semantics are tested against independent synthetic examples and exact pinned case snapshots.

No A/B trial has been run. No provider has been invoked. No ground-truth or primary eligibility field has been changed.
