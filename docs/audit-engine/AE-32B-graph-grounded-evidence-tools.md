# AE-32B — Graph-Grounded Repository Evidence Tools

## Purpose

AE-32B turns the existing `SemanticGraph` and `SemanticGraphAnalysisService` into a bounded, read-only evidence interface suitable for a future LLM investigation loop. It is the tool layer between AE-32A's architecture inventory and AE-32C's interactive model orchestration.

AE-32B does **not** call an LLM, execute target-repository code, run shell commands or tests, make network requests, apply patches, write into the inspected repository, commit, or push.

## Tool interface

Python API:

```python
from audit_engine.semantic_audit.ae32b import RepositoryEvidenceTools

tools = RepositoryEvidenceTools(
    repo_root=".",
    source_revision="<optional exact source commit>",
    runner_revision="<optional trusted runner commit>",
)
result = tools.invoke("graph_neighbors", {
    "node": "audit_engine/semantic_audit/ae31/diagnosis.py",
    "direction": "both",
    "max_depth": 2,
})
```

The returned object is JSON-compatible and includes a schema version, status, structured result or safe error, source-manifest SHA-256, graph fingerprint, and optional source/runner revisions. The catalog returned by `build_tool_definitions()` uses OpenAI-compatible function-tool JSON schemas but does not depend on a particular LLM provider.

CLI examples:

```bash
python -m audit_engine.semantic_audit.ae32b --list-tools
python -m audit_engine.semantic_audit.ae32b --repo-root . \
  --request-json '{"tool":"repository_summary","arguments":{}}'
python -m audit_engine.semantic_audit.ae32b --repo-root . \
  --request-json '{"tool":"find_related_tests","arguments":{"target":"audit_engine/semantic_audit/ae31/diagnosis.py"}}'
```

The CLI performs one request per process. AE-32C should create one `RepositoryEvidenceTools` instance per inspected snapshot and reuse it across multiple model tool calls so that the source manifest and graph fingerprint remain stable for the investigation.

## Available tools

| Tool | Purpose |
|---|---|
| `repository_summary` | Return snapshot counts, graph size, relation counts, parse/scope status, and provenance. |
| `search_repository` | Search indexed source, configuration, workflow, and documentation text with bounded line snippets. |
| `read_source_file` | Read an exact repository-relative path and bounded line range. |
| `search_symbols` | Locate AST-discovered classes, functions, and async functions. |
| `graph_neighbors` | Query direct or transitive graph relationships through `SemanticGraphAnalysisService`. |
| `graph_path` | Test a bounded path between two graph entities using the existing graph analysis service. |
| `find_related_tests` | Find tests that statically import a module or explicitly reference it in text. |
| `find_workflow_context` | Find workflows with direct invocation or bounded transitive import paths to a target. |
| `search_decision_history` | Search the scoped decision, outcome, action, rule, link, and audit decision records. |

## Graph projection

The source graph is reconstructed from the exact AE-32A manifest and its AST-derived import/workflow observations. It uses the repository's canonical `SemanticGraph` data model and `SemanticGraphAnalysisService` for graph-neighbor and path queries.

Observed node types include source files, Python modules, Python symbols, workflow definitions, test files, documentation/configuration files, structured decision-memory records, and AE-32A static findings. Relationship types include `IMPLEMENTS`, `IMPLEMENTED_BY`, `DEFINES`, `MEMBER_OF`, `IMPORTS`, `TESTS`, `INVOKES`, `SUPPORTED_BY`, `PACKAGE_ENTRYPOINT`, `CONTAINS_RECORD`, `REFERENCES_DECISION`, `OUTCOME_FOR_ACTION`, `DERIVED_FROM_DECISION`, `DERIVED_FROM_ACTION`, `DERIVED_FROM_OUTCOME`, and `LINKS_DECISION`.

Each edge is an observed structural relationship with source path/line metadata where available. A static import does not prove runtime execution; a workflow command does not prove that a workflow ran; and a finding supported by a file is not itself proof that the finding is correct. Graph observations are not automatically promoted to validated conclusions.

## Evidence and provenance

- The source inventory is generated by AE-32A without importing or executing target Python modules.
- Included files are re-read only after checking path boundaries, symlinks, and the exact manifest SHA-256. If a file changes during index construction, indexing fails closed.
- Evidence paths are repository-relative. Results include source file hashes and line references where available.
- The graph fingerprint and source-manifest digest are included in every tool response.
- Query IDs are deterministic per query parameters, avoiding collisions in the graph analysis working memory when a single tool server serves multiple different requests.
- Tool arguments are allowlisted, input lengths and result counts are bounded, and unknown tool names/arguments are rejected.
- Credential-like paths are blocked. Secret-like literals and bearer/token shapes are redacted from file/snippet output.
- No tool accepts shell commands, arbitrary URLs, write paths, patch content, or execution instructions.

## Boundaries and known limitations

1. This is a source-level graph projection, not a runtime call graph. Dynamic imports, reflection, generated code, and workflow expression expansion may not be represented.
2. `search_repository` and `search_decision_history` are bounded lexical searches, not vector/embedding retrieval. They provide the evidence retrieval interface first; a future semantic retrieval adapter can be added behind the same evidence contract if the repository has a suitable tested backend.
3. Test relationships combine static imports with explicit text references. They do not claim that a test was collected or executed by a workflow.
4. Workflow context can follow a bounded static import path from an invoked module to a source module. It cannot prove runtime reachability.
5. Decision-history matches are retrieval context, not automatically authoritative decisions. AE-32C must ask the model to cite and weigh the returned evidence rather than treat prior records as unquestionable truth.
6. The tools are not yet wired into AE-31 or a live provider. That connection, tool-call loop, stopping rules, and live diagnosis-quality evaluation belong to AE-32C.
7. Repair, testing, and promotion remain separate concerns. AE-32B has no write/execute/repair tool.

## Validation

The G9.41 profile runs the AE-32B tests, AE-32A architecture-audit tests, AE-24 through AE-31 focused regression, and the repository's full `tests/` regression suite. The local test suite verifies graph service use, exact source evidence, bounded requests, secret redaction, path traversal rejection, deterministic fingerprints, decision-history scoping, workflow/test discovery, and no target-code execution or repository mutation.
