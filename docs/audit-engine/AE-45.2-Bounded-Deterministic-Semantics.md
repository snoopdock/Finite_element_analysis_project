# AE-45.2 — Bounded deterministic semantic primitives

**Status:** implementation draft; CI validation pending  
**Branch:** `stage1/section-uuids`  
**Depends on:** A0 validated contracts and A1 validated rule catalog

## 1. Scope

A2 begins implementing reusable deterministic semantics, not a complete A condition runner. The module accepts source text, explicit function identifiers and task-visible contract values. It does not load case records, machine-reference registries, expected findings from case JSON, scorer outputs or provider credentials.

## 2. Implemented primitives

`tools/ae32d_deterministic_rules.py` currently provides:

- bounded control-flow inspection for a deliberately small function subset (`Assign`, `AnnAssign`, `AugAssign`, `If`, `Return`, `Pass`);
- conservative detection of a local name read at a return without a reaching assignment;
- a safe expression interpreter for literals, names, bounded arithmetic, unary operators, simple comparisons and conditional expressions;
- a pure function-subset interpreter for assignments, conditionals and returns;
- static detection of an exception handler that catches a task-specified exception and returns normally rather than re-raising;
- detection of a stale intermediate assignment bypassed by the return sink, paired with task-visible input/output comparison;
- observation of an attribute read not declared on a visible provider class, with an explicit abstention rather than a defect claim.

The interpreter never uses `eval`, imports target code, invokes repository functions, performs network access or writes to source.

## 3. Fail-closed semantics

Unsupported syntax is not approximated. Loops, try statements in the control-flow analyzer, unsupported assignment targets, calls, attributes, dynamic signatures, excessive expression depth and out-of-budget powers are reported as unsupported. A rule caller must convert unsupported or incomplete evidence into abstention or an execution error according to the report contract; it must not silently skip the unsupported path.

The provider-attribute primitive is intentionally observational. A static absence from one class body does not rule out dynamic attributes, inheritance, wrappers or runtime injection. Its result is therefore `abstain` when a visible mismatch exists.

## 4. Tests

`tests/semantic_audit/test_ae32d_deterministic_rules.py` covers:

1. unbound local on one conditional path;
2. complete initialization as a counterexample;
3. unsupported control flow;
4. exception suppression against a propagation contract;
5. re-raise as counterevidence;
6. stale intermediate bypass at the output sink;
7. corrected dataflow as a counterexample;
8. rejection of executable calls by the safe expression evaluator;
9. dynamic attribute mismatch as observation plus abstention.

These are unit-level semantic checks over synthetic source snippets. They do not constitute a scored AE-32D run, do not validate every Python semantic, and do not authorize a condition runner.

## 7. Pinned fixture integration layer

Added `tests/semantic_audit/test_ae32d_pinned_rule_fixtures.py`. It checks out no source itself; it consumes the three immutable source checkouts already prepared by the AE-32D workflow and verifies each checkout's actual `git rev-parse HEAD` against its expected SHA before reading fixture files.

The tests exercise:
- branch-unbound detection against the exact case-matrix fixture and complete-initialization control;
- exception suppression against the exact extended-case fixture and its task-visible expected-behavior contract;
- stale intermediate/sink mismatch against the exact extended-case fixture and its declared input/output example;
- provider-interface mismatch as observation plus abstention against the exact controlled incident source;
- ambiguous dynamic-provider evidence as abstention when the runtime factory implementation is absent from the fixture bundle.

Only source fixture files and task-visible fixture contracts are read. The test never loads the case JSON, `ground_truth`, machine-reference registry or adjudication metadata. The workflow now runs this integration layer with explicit paths to the immutable checkouts.
