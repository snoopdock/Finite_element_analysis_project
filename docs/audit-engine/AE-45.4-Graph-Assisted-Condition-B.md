# AE-45.4 — Graph-assisted deterministic condition B

**Status:** implementation and tests committed; full workflow validation pending  
**Branch:** `stage1/section-uuids`  
**Depends on:** validated A0–A3 contracts and deterministic baseline

## 1. B treatment

Condition B is implemented as the exact A baseline plus bounded AE-32B graph retrieval. It first runs the same A adapter using the same sanitized task projection, source commit, task digest, rules, report schema and evidence scope. It then builds a temporary graph snapshot from a byte-for-byte copy of only the files admitted by A's source manifest. The copied-scope digest must equal A's manifest digest before graph construction begins.

This avoids exposing the full repository graph to a case whose declared evidence scope is limited to a fixture. Human-readable scope descriptors do not silently expand the graph snapshot.

## 2. Graph backend selection

B currently selects the NetworkX adapter for bounded adjacency and path queries. This is a task-relevance choice for source relationship traversal, not a performance comparison or universal backend ranking. Other graph backends remain alternative computation options for tasks whose requirements justify them.

The selected backend must report that its adapter is wired into the AE-32B query path. A reference fallback does not count as native graph execution for this B configuration.

## 3. Frozen retrieval policy

The versioned policy performs:
1. one `repository_summary` request for graph snapshot identity and completeness;
2. bounded `graph_neighbors` requests for each declared Python source file;
3. `search_symbols` for a function named in the task-visible expected-behavior contract;
4. bounded symbol-neighbor and file-to-symbol `graph_path` requests for resolved in-scope symbols;
5. `find_related_tests` only when the declared scope explicitly permits related-test discovery;
6. `trace_execution_context` only when the task statement asks about runtime, workflow or entrypoint context.

The policy excludes `discover_case_context`, `search_decision_history`, and other tools that could expose hidden benchmark metadata. It uses no LLM to choose queries.

## 4. Snapshot and report integrity

The B report contains:
- the complete A report as `baseline_report`;
- the exact A `baseline_config_digest`;
- graph source revision, graph manifest digest, graph fingerprint, projection version, index completeness, backend name and graph size;
- every bounded retrieval request, status, truncation state, response digest and sanitized payload;
- the same A findings and decision, plus graph retrieval trace and graph limitations.

B must not delete or rewrite A evidence. Its source/task digests are identical to A's. Its own config digest binds the A baseline digest, graph policy, graph fingerprint, selected backend and implementation source hashes.

**Important v0.1 limitation:** graph evidence is additive; no graph-specific diagnostic rule is enabled yet. B therefore retains A's decision. This is an explicit retrieval-only stage, not a claim that graph retrieval improved diagnosis. Later graph-specific rules require their own sufficient-evidence, counterevidence and abstention tests.

## 5. Runtime dependency boundary

The AE-32D workflow now installs PyYAML and NetworkX in addition to jsonschema because AE-32B imports YAML parsing and the selected graph traversal adapter. It does not install or invoke provider SDKs, and no credentials or external model calls are involved.

## 6. Validation

`tests/semantic_audit/test_ae32d_graph_assisted_audit.py` checks:
- exact A/B pairing and byte-identical embedded A report;
- preservation of the A decision and source/task digests;
- graph snapshot provenance and selected NetworkX backend;
- actual AE-32B query-path wiring;
- graph-neighbor, symbol and path retrieval;
- conditional related-test and execution-context operations for the provider-interface scope.

The workflow dependency step was corrected to install PyYAML and NetworkX.
