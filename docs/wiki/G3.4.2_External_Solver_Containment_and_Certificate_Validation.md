# G3.4.2 — External Solver Containment and Certificate Validation

## Purpose

G3.4.2 introduces the first controlled path from the semantic audit architecture to an external solver process. The milestone is intentionally narrower than “enable SAT/SMT.” It establishes the containment, identity, protocol, and certificate-validation rules that any future external solver must obey.

## Architecture

```text
VerificationObligation
        ↓
HighAssurancePolicy
        ↓
controlled-external-cnf adapter
        ↓
fixed registered process specification
        ↓
executable SHA-256 verification
        ↓
strict JSON subprocess boundary
        ↓
external solver response
        ↓
protocol + request + input + solver identity binding
        ↓
repository-owned certificate validation
        ↓
ValidationEnvelope + Witnesses
        ↓
VerificationDecision / EvidenceState
```

The external process does not decide evidence state.

## Controlled external is not sandboxed

The runner provides concrete process controls:

- absolute registered executable path;
- executable digest verification before every run;
- fixed registered arguments;
- no shell;
- bounded JSON input and output streams;
- mandatory timeout;
- process-tree termination on timeout/output overflow;
- ephemeral working directory;
- minimal environment;
- digested execution transcript.

It does **not** claim OS-level network isolation or full filesystem isolation. Both gaps require explicit risk acknowledgement before execution. The transcript records both as `false` so later audit readers cannot mistake controlled external execution for sandboxing.

## Certificate semantics

### SAT

A SAT result can reach `VALIDATED` when the solver supplies a complete Boolean assignment and repository-owned code independently checks that every declared variable is bound and every CNF clause evaluates to true.

This uses:

`certificate_complete_within_scope`

because the certificate completely discharges the satisfiability claim without reproducing the producing solver's search.

### UNSAT

For bounded CNF instances within the repository-owned independent-check limit, an external UNSAT claim is rechecked by exhaustive assignment enumeration. Only then can it reach `VALIDATED` with `exhaustive_within_scope`.

For a larger UNSAT claim without a supported proof checker:

```text
external says UNSAT
        ↓
protocol-valid observation
        ↓
OBSERVED + PARTIAL
```

It is not promoted to validated evidence.

If independent checking finds a model, the external UNSAT claim is overruled and the counterexample becomes validated evidence.

## Activation

`controlled-external-cnf` is not in the default high-assurance adapter registry. Its orchestration profile is metadata only.

Execution requires all of:

1. trusted construction of the process specification;
2. trusted registration of the adapter;
3. solver mechanism permission;
4. controlled-external containment permission;
5. side-effect policy permission;
6. explicit adapter activation;
7. explicit acknowledgement of missing OS-level network/filesystem isolation;
8. sufficient orchestration budget.

## Formal backends remain inactive

G3.4.2 does not activate:

- `formal/sat`;
- `formal/smt`;
- `formal/cpsat`;
- `formal/lean`;
- `formal/router.py`.

Those systems require real adapters and, for validated negative results, independently checkable proof/certificate semantics.

## Semantic boundary

The central rule remains:

```text
external process output
        ≠
validated evidence
```

Validated evidence exists only after the repository can independently validate the solver's witness or proof within an explicit validation envelope.
