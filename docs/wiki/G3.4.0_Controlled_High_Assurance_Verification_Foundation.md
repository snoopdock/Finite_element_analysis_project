# G3.4.0 Controlled High-Assurance Verification Foundation

G3.4.0 introduces an explicit boundary for stronger verification mechanisms. A result is never described merely as "high assurance"; it must include the exact mechanism, tool/version, subject digest, validation envelope, witness set, and policy decision that allowed execution.

The first two concrete mechanisms are deliberately modest but real: a deterministic Python AST verifier for forbidden static import statements, and a deterministic SHA-256 artifact-integrity verifier. Both operate in-process, read-only, without network access or side effects.

The Python verifier is exhaustive only for `ast.Import` and `ast.ImportFrom`. Dynamic imports through `importlib`, `__import__`, generated code, or runtime loading are explicitly excluded from the validation envelope. This distinction prevents a static syntactic check from being misreported as a complete runtime dependency proof.

The existing SAT, SMT, CP-SAT, and Lean directories remain placeholders. G3.4.0 does not activate or profile them. Future solver work must provide real adapters, containment, certificates or proof witnesses, and validation-envelope semantics before orchestration can schedule them.

High-assurance adapters bridge into the existing G3.1 `Verifier` protocol, so their results become ordinary immutable `VerificationReceipt` artifacts and remain compatible with G3.3 cost-aware orchestration. The orchestration layer receives separate resource profiles; adapter implementation itself never learns cost or priority.
