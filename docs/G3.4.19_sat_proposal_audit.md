# G3.4.19 — SAT Proposal and Generated-Text Audit Trace

## Purpose and boundary

This stage links a *proposed* change or generated passage to historical decision-memory records. It extends G3.4.18 retrieval rather than creating a second memory store. It audits **referential integrity** and **traceability**, not the truth of engineering claims, formal SAT satisfiability, or the safety of a proposed change. It cannot promote learning rules, write to source memory, approve a decision, or execute SAT actions.

Each nonempty input line is treated as a claim. To cite an existing decision-memory record in a claim, use `[[DEC-G3.4.13-001]]`, `[[ACTION-G3.4.15-001]]`, `[[OUTCOME-G3.4.16-001]]`, or `[[RULE-G3.4.17-001]]`. References are resolved using actual files, their IDs and SHA-256 digests. Citations are *not* proof that the cited text supports the statement: they merely provide an accountable reviewer a place to inspect.

## Result

The `sat-proposal-audit/v1` JSON includes the exact untrusted draft text, claim-by-claim explicit citations, missing citation flags, source file paths and hashes, a ranked historical context (from G3.4.18), conflict caveats, source Git commit if this is a Git checkout, a deterministic audit SHA-256, and mandatory human-review gates. Every report has `automated_sat_action_allowed: false`, `human_review_required: true`, and `writeback_to_decision_memory_allowed: false`.

`review_gates.citation_trace_complete` only means each claim has at least one syntactically valid reference to an existing source. It **never** means factual support, semantic entailment, quality of generated text, or a satisfiable decision plan. All historical source text is untrusted data; it is never executed as instructions.

## GitHub-only usage (manual)

Place `MAIN_BRANCH/.github/workflows/07_manual_sat_proposal_audit.yml` on `main`. Place the stage files on `stage1/section-uuids`. Do **not** replace the existing validation dispatcher. Trigger `Actions → Manual Validation Dispatcher` with profile `G3.4.19` to validate the implementation.

Separately, select `Actions → Manual SAT Proposal and Text Audit` (use workflow from `main`), choose your development branch, enter a search query and proposed text (one claim per line), and download the resulting audit JSON. This flow has **only** `workflow_dispatch`, no `push`, no write permission, and no persistence outside the normal expiring GitHub artifact. Do not put confidential text in workflow inputs; authorized repository collaborators may be able to view run metadata.

## Suggested audit checklist

1. Verify relevant commits and each `source_sha256` against the Git history and repository contents.
2. Check the cited decision actually supports the generated claim; do not infer support from IDs or word overlap.
3. Resolve `pending_action_with_successful_feedback`, incomplete references, and unapproved rule candidates before drawing conclusions.
4. Independently review external evidence bundles and confirm applicability to the proposed engineering situation.
5. Record any approved decision through a separate governed workflow in a later milestone; this feature does not implement approval.

## Limits

G3.4.19 is an advisory review record. Actual SAT formula creation, solver execution, policy binding, approval and persistent learned-rule updates are not implemented in this milestone. Lexical ranking remains approximate, and incomplete retrieval does not imply the absence of relevant historical evidence.
