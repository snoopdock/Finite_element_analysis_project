# Finite Element Analysis Project

An automated pipeline that writes a technical guideline about the Finite Element Method (FEM). It searches academic sources, extracts knowledge, writes sections, and assembles a LaTeX document. It runs on a schedule and improves itself over repeated cycles.

**This project was built by LLMs.** A human provided the problem domain (FEM) and the conceptual direction. Every line of code, every architectural decision, every prompt, and every word of documentation was generated by large language models. The human's role was to set the goal, review the output, and decide what to build next.

> For a record of problems encountered during development and how they were solved, see the [Project Wiki](../../wiki).

---

## What the Pipeline Does

Each cycle runs four phases in order:

1. **RESEARCH** — Search arXiv and Wikipedia for new FEM sources. Zero LLM calls.
2. **EXTRACT** — Read new sources and extract concepts, equations, procedures, and rules into a structured knowledge base. One LLM call.
3. **WRITE** — Write or rewrite sections of the guideline using the knowledge base. Up to five LLM calls.
4. **ASSEMBLE** — Combine all sections into a single LaTeX document. Zero LLM calls.

The pipeline tracks its own state between cycles. It remembers which sources it has already read, which sections it has already written, and which sections passed or failed quality checks. On each new cycle, it decides what still needs work and skips what is already done.

### Phase Details

| Phase | Input | Output | LLM Calls | Neuron Cost |
|---|---|---|---|---|
| RESEARCH | Search queries from config | evidence.json | 0 | 0 |
| EXTRACT | New sources | research.json | 1 | ~500 |
| WRITE | Knowledge base | sections.json | 1-5 | 500-2500 |
| ASSEMBLE | Sections | guideline.tex | 0 | 0 |

## How the Pipeline Decides What to Work On

The pipeline does not rewrite every section on every cycle. It computes a score for each section and only works on the sections that need attention.

### The Indicator Score

For each section, the pipeline computes a score called eta:

eta = w_L * L + w_U * U + w_A * A

Where:
- L (Leverage): How many other sections depend on this one. Range: 0 to 1.
- U (Instability): How recently this section failed a quality check. Range: 0 (stable) to 1 (unstable or never checked).
- A (Anomaly): Whether the quality checker flagged a problem with this section in the last cycle. Value: 0 or 1.

The weights are set in config.yaml. The defaults are w_L = 0.4, w_U = 0.4, w_A = 0.2.

### The Marking Rule

After computing eta for every section, the pipeline sorts them from highest to lowest score. It marks sections for rewriting until the marked set accounts for at least 75% of the total eta across all sections. This is called the equilibration strategy.

Sections that are not marked are left unchanged for that cycle.

### Skipping Work

If all sections are stable (eta variance is low, no quality check failures, no pending adjustments), the pipeline skips the WRITE phase entirely. This saves LLM API calls.

The specific conditions for skipping are:
- Eta variance across all sections is below 0.1.
- Zero invariant violations were recorded in the last cycle.
- Zero adjust actions fired in the last cycle.
- No new sources were found in the RESEARCH phase.

If all four conditions hold, the WRITE phase is skipped and only RESEARCH and ASSEMBLE run.

**References for this section:**
- The indicator function and marking strategies are adapted from adaptive mesh refinement. See Dorfler, W. (1996). "A convergent adaptive algorithm for Poisson's equation." SIAM Journal on Numerical Analysis, 33(3), 1106-1124.
- The principle of allocating limited computation where it produces the most improvement comes from Zilberstein, S., and Russell, S. (1996). "Using anytime algorithms in intelligent systems." AI Magazine, 17(3), 73-83.
- The Observe-Analyze-Adjust loop pattern is from Kephart, J. O., and Chess, D. M. (2003). "The vision of autonomic computing." IEEE Computer, 36(1), 41-50.

## How the Pipeline Finds Missing Knowledge

The pipeline does not only search for topics listed in config.yaml. It actively looks for gaps in its own knowledge base using a two-step process.

### Step 1: Fetch a Reference Taxonomy (Context-Free Track)

The pipeline queries the Wikipedia API for pages related to FEM. It extracts the section headings from those pages. These headings form a list of topics that a complete FEM guideline should cover.

This step uses no LLM calls. It costs nothing. The taxonomy is independent of the pipeline's current state, which makes it a context-free evidence track.

### Step 2: Compare Against the Knowledge Base (Context-Aware Track)

The pipeline sends the Wikipedia topic list and a summary of the current knowledge base to an LLM. The LLM identifies which topics from the Wikipedia list are missing or poorly covered in the knowledge base.

The LLM returns up to three missing topics and a search query for each one.

### Step 3: Search for the Missing Topics

The pipeline adds the generated search queries to its arXiv and Wikipedia searches for the current cycle.

The two-track design (one track independent of context, one track dependent on context) follows the principle that combining context-aware and context-free evidence produces better decisions than relying on either alone.

**References for this section:**
- The two-track evidence approach is described in the project's internal framework document, "Dynamic Iterative Process Segmentation Framework - Formalized Edition," Section 5.
- Wikipedia API documentation: https://en.wikipedia.org/api/rest_v1/
- arXiv API documentation: https://info.arxiv.org/help/api/
- The principle of combining context-aware and context-free evaluation is from Ashby, W. R. (1956). An Introduction to Cybernetics. Chapman and Hall.

## How the Pipeline Writes Sections

The pipeline does not ask the LLM to write an entire section in one call. It breaks each section into sub-tasks:

1. Generate an outline. The LLM produces a list of 3 paragraph topics. One LLM call.
2. Write each paragraph. The LLM writes one paragraph at a time. Each paragraph is checked against the previous paragraphs to prevent repetition. One LLM call per paragraph.
3. Assemble. The paragraphs are joined into a section. No LLM call.
4. Validate. The section is checked for minimum length and citation presence. No LLM call.

### Citation Enforcement

Every paragraph must cite its sources. The pipeline provides the LLM with a list of allowed source IDs. If the LLM produces a citation that is not in the allowed list, the citation is removed. If a paragraph contains no valid citations, the pipeline logs a warning.

### Repetition Prevention

Before accepting a new paragraph, the pipeline computes the word overlap between the new paragraph and every previous paragraph in the same section. If the overlap exceeds 50%, the paragraph is rejected.

### Section Splitting and Merging

If a section has fewer than 300 words, it is flagged as "too short" and marked for expansion in the next cycle. If two adjacent sections have more than 60% word overlap, they are flagged as "redundant" and marked for merging.

Only one structural change (split or merge) is applied per section per cycle. This prevents cascading changes that are hard to trace.

**References for this section:**
- The sub-task decomposition follows the principle that complex tasks should be broken into smaller, independently verifiable units. See Simon, H. A. (1962). "The architecture of complexity." Proceedings of the American Philosophical Society, 106(6), 467-482.
- The Input-Process-Output contract pattern for each sub-task is from Parnas, D. L. (1972). "On the criteria to be used in decomposing systems into modules." Communications of the ACM, 15(12), 1053-1058.
- The repetition check uses Jaccard similarity. See Jaccard, P. (1901). "Etude comparative de la distribution florale dans une portion des Alpes et des Jura." Bulletin de la Societe Vaudoise des Sciences Naturelles, 37, 547-579.
- The bounded adjustment rule (one change per component per iteration) is from the project's internal framework document, Section 7.

## How the Pipeline Checks Its Own Work

After writing, the pipeline runs a quality check on every section. This check is called the Observe-Analyze-Adjust (OAA) loop.

### Observe

The pipeline measures:
- Word count of each section.
- Number of citations in each section.
- Word overlap between adjacent sections.

### Analyze

The pipeline compares the measurements against thresholds:
- A section with fewer than 300 words is flagged as "too short."
- Two adjacent sections with more than 60% word overlap are flagged as "redundant."
- A section with zero citations is flagged as "uncited."

### Adjust

Based on the analysis, the pipeline decides one of three actions:
- Split: If a section is too short, mark it for expansion in the next cycle.
- Merge: If two sections are redundant, combine them.
- Do nothing: If no problems are found, leave the sections unchanged.

### Hysteresis

The OAA loop uses a hysteresis band of d = 2 cycles. Once a section is marked as stable, it cannot be re-flagged for at least 2 cycles. This prevents oscillation caused by noise in a single cycle's measurements.

**References for this section:**
- The OAA loop is a technical implementation of the closed-loop control pattern from Wiener, N. (1948). Cybernetics: Or Control and Communication in the Animal and the Machine. MIT Press.
- The hysteresis mechanism that prevents feedback loop oscillation is from control theory. See Astrom, K. J., and Murray, R. M. (2008). Feedback Systems: An Introduction for Scientists and Engineers. Princeton University Press.
- The bounded adjustment rule (one change per component per iteration) is from the project's internal framework document, Section 7.

## Formal Verification Layer (Planned)

The pipeline includes a directory structure for formal verification. This layer is not yet active. When it is active, it will check mathematical claims in the generated text using automated solvers.

### Routing Rule

The type of mathematical question determines which tool to use:

| Question being asked | Tool to use |
|---|---|
| Does a valid solution exist? | SAT or SMT solver |
| What is the best solution? | CP-SAT or MILP solver |
| Is this property true for all inputs? | Lean theorem prover |
| How many valid solutions exist? | Counting procedure |

These are not levels in a hierarchy. No solver is universally better than another. The correct principle is: choose the solver that can exploit the mathematical structure of the problem.

### Verification Budget Gate

The pipeline will only invoke a formal solver if the section's indicator score eta exceeds a threshold tau. This prevents unnecessary solver calls on sections that are already stable.

Sections whose content is inherently informal (such as creative writing) are exempt from the formal layer regardless of eta. This exemption is recorded explicitly in the iteration log.

**References for this section:**
- Biere, A., Heule, M., van Maaren, H., and Walsh, T. (eds.). (2021). Handbook of Satisfiability (2nd ed.). IOS Press.
- Barrett, C., Fontaine, P., and Tinelli, C. "The SMT-LIB Standard." https://smt-lib.org/
- Google OR-Tools CP-SAT documentation: https://developers.google.com/optimization/cp
- Lean 4 documentation: https://lean-lang.org/
- The distinction between existence questions and universal questions is from the project's internal document, "Satisfiability, SAT, SMT, CP-SAT, Optimization, and Formal Verification," Sections 11 and 14.

## Repository Structure

| Directory | Purpose |
|---|---|
| main.py | Entry point. Calls core/pipeline.py. |
| config.yaml | All configuration: weights, thresholds, models, budgets. |
| core/ | Phase sequencing, convergence detection, budget tracking, state persistence. |

| formal/ | Formal verification layer: SAT, SMT, CP-SAT solvers and Lean 4 proofs. Not yet active. |
| specs/ | IPO contracts for each phase, system invariants, pipeline objectives. |

| state/ | Persistent state between cycles (current_state.json). |
| output/ | Generated files: evidence, knowledge base, sections, LaTeX, reports. |
| .github/workflows/ | GitHub Actions automation. Runs the pipeline on a schedule. |

### Formal Layer Directory

The formal/ directory contains:
- router.py: Routes questions to the correct solver based on question type.
- budget_gate.py: Threshold gate (tau) for solver invocation.
- sat/: Boolean SAT solver interface.
- smt/: Satisfiability Modulo Theories solver interface.
- cpsat/: Constraint Programming with SAT solver interface.
- lean/: Lean 4 theorem prover project.
  - FEA/FEM/: FEM mathematical proofs (WeakForm, Galerkin, Stiffness, Convergence).
  - FEA/Pipeline/: Pipeline correctness proofs (Contracts, Invariants, Segmentation).
  - FEA/Verification/: Solver certificate verification (SatCert, OptimCert).

## Running the Pipeline

### Locally

Set environment variables and run:

export CLOUDFLARE_ACCOUNT_ID="your_account_id"
export CLOUDFLARE_API_TOKEN="your_api_token"
python main.py --config config.yaml

### On a Schedule

The GitHub Actions workflow runs the pipeline every 6 hours. It commits the updated knowledge base, sections, and LaTeX document back to the repository.

To change the schedule, edit .github/workflows/FEA-pipeline.yml:

on:
  schedule:
    - cron: "0 */6 * * *"

Warning: The Cloudflare Workers AI free tier provides 10,000 neurons per day. At 6 calls per cycle (approximately 3,000 neurons), running hourly would exceed this limit. Reduce max_llm_calls_per_run if you increase the frequency.

## Limitations

1. The pipeline uses 8B parameter LLMs. These models sometimes ignore instructions, produce repetitive text, or fail to include citations. The algorithmic guardrails (repetition check, citation allowlist) catch many of these failures, but not all.

2. The knowledge base is small. After 10 cycles, it contains roughly 5-10 concepts, 3-5 equations, and 3-5 rules. This is not enough to write a comprehensive FEM guideline. The pipeline needs many more cycles to accumulate sufficient knowledge.

3. The formal verification layer is not active. The directory structure exists, but no solver is called. This is intentional: the pipeline needs to reach a stable state before formal verification adds value.

4. The Wikipedia gap detector depends on Wikipedia's article structure. If the FEM article changes its section headings, the taxonomy changes. This is not a problem in practice, but it means the gap detector's output is not fully deterministic across long time spans.

5. The indicator weights, marking threshold, and hysteresis window are stated by convention, not derived from data. Establishing optimal values would require running the procedure on genuine processes and comparing outcomes, which is outside the scope of the current implementation.

**References for this section:**
- The limitation that small models produce unreliable structured output is documented in Tam, D., et al. (2024). "Let Me Speak Freely? A Study on the Impact of Format Restrictions on Performance of Large Language Models." arXiv preprint, arXiv:2404.14394.
- The acknowledged limitation that framework parameters are set by convention is from the project's internal framework document, Section 13.5.
